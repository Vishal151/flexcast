# Journal

One entry per stage: what was built, what surprised us, open questions.

## Stage 0 — Explore the data
- Built `scripts/explore_api.py` and `scripts/record_fixtures.py` over one shared request list, plus a fixture manifest for respx and mock_upstream. Recorded 26 responses (stored as indented JSON for reviewable diffs, 5.4 MB) for a normal day and both 2025 DST days. Every SPEC §2 Elexon path exists in the live OpenAPI spec.
- Surprises: WINDFOR is hourly with 8 vintages/day on a schedule that is neither UTC- nor London-fixed. NDF publish-window queries are capped at 1 day. MID `from`/`to` are instants, not dates. N2EX MID drops periods on the autumn DST day. My own hand-written Agile window was an hour off on the spring DST day, which is the case for deriving windows from London dates in code.
- Open: does the system-prices endpoint expose settlement-run revisions (`createdDateTime` is ~D+1)? How much of the target day does the latest NDF vintage before D-1 09:00 actually cover? That's the Check yourself question, and it may push decision time or feature design.

## Stage 1 — Core library, local only
- Built config (env-only), fsspec storage (atomic writes), a settlement helper checked against Elexon's own mapping for 144 real periods, Elexon/Octopus clients (retry/backoff, chunking to the 1-day/7-day caps, pydantic validation that also checks settlement date/period against start_time), idempotent ingest (merge on natural key, deterministic Parquet, rejects kept in `rejects/`) and the battery MILP (PuLP + HiGHS). Backfilled 730 days × 6 datasets (40 MB) in ~3.5 min with no failures; a live re-ingest is byte-identical.
- Surprises: PuLP 4 no longer bundles CBC and changed its API (`prob.add_variable`, `LpSolveStatus`), so we added `highspy`. `AGILE-BB-*` is the Bulb-branded Agile, not business. With perfect foresight on system prices a 10 kWh battery makes £278/yr. Degradation is the biggest lever (£656/yr at 0p/kWh vs £278 at 2p). 90%→80% efficiency costs about 20% (£278→£221). Agile gives £648/yr: its retail formula amplifies wholesale spreads and adds a 16:00–19:00 uplift, so it's not a market price.
- MILP vs LP: the binary removes simultaneous charge/discharge (39 of 48 periods in the relaxed LP at −£1000/MWh) but only changes £ by 2p there. The battery can still "earn from losses" by alternating periods, which is physically allowed.
- Open: the 2p/kWh degradation default needs a defensible source before Stage 2 results; Agile export would be paid at the Outgoing rate, so the symmetric-price Agile number overstates value.

## Stage 2 — Forecasting and backtest, local only
- Built `history.py` (the only route from stored data to features; every row has `available_at`), point-in-time `features.py` (23 features, NDF stitched per period, London-clock-time lags), NaiveLastDay / SeasonalNaive / LGBMQuantile behind one interface with text-file serialisation, and a rolling-origin backtest that keeps forecasting and £ valuation separate. Leakage test = poison everything available at/after the decision (features must not change) + per-source provenance + pinned availability rules.
- Result (2025-10-20..2026-10-19, 2p/kWh): perfect £271/yr; LightGBM £33/yr (12% of perfect, MAE 30.6); naive −£149, seasonal −£155 (MAE 44–45). The imbalance price is so noisy (D-2 correlation 0.07) that copying a past day trades on noise and loses money, so "idle = £0" is the real bar, not naive.
- Surprises: real-time system prices publish ~48 min after period start, but the endpoint returns the latest revision with its own (D+1) timestamp, so the historical series is revised values (caveat in results). Mutation testing showed the poisoning test can't catch a *wrong availability rule* (the poison moves with it), so the rules got their own test. PuLP→HiGHS last stage, LightGBM→libomp this stage: native deps will matter in the Dockerfile (`libgomp1`).
- Open: a risk-aware schedule (only trade when the p10/p90 spread clears losses + degradation) looks like the biggest lever for £, bigger than a better p50. Degradation cost is decisive (LightGBM £174/yr at 0p vs £3 at 4p).
- Stage 2b, risk-aware scheduling: plan buying at p50 + α(p90 − p50) and selling at p50 − α(p50 − p10), with α chosen on the 6 months before the test window. The hypothesis was wrong: α = 0 won on validation (£24.6/yr vs £23.0 at 0.25 and £0 at 1) and on the test window in hindsight too. Reason: LightGBM's p50 is already shrunk towards the mean (median forecast daily spread £68/MWh vs £122 actual; trades 76% of days, 11.7 kWh/day vs 31). Its p10–p90 band (£77) is wider than its typical spread, so any α > 0 counts the same uncertainty twice. The losing naive baselines have real-sized spreads at the wrong times and no uncertainty band; that's where an uncertainty gate would help.

## Stage 3 — Containerise and emulate GCP locally
- Built a multi-stage Dockerfile (uv builder, slim runtime, libgomp1, uid 10001, `ENTRYPOINT flexcast`), `compose.yaml` (fake-gcs-server, bucket init, upstream-mock replaying the fixture manifest, api, ingest/train/plan jobs with per-job entrypoints), `flexcast train|plan|serve`, a read-only FastAPI (`/health`, `/schedule`, `/forecast`, `/metrics`), and 13 integration tests (ingest→train→plan through containers, byte-identical re-ingest through the real GCS client, API contract on a non-default PORT, failed upstream → non-zero exit). From an empty Docker cache, `make up && make itest` passes in 77 s.
- Emulator vs real GCS (cover in the Stage 5 smoke test): (1) gcsfs 2026.10 enables an experimental zonal/HNS client by default that probes buckets over gRPC; the emulator can't answer, so every call hung for 60 s. Disabled with `GCSFS_EXPERIMENTAL_ZB_HNS_SUPPORT=false` in every profile. (2) fake-gcs doesn't implement `moveTo`; my temp-file-then-rename write fell back to copy/delete and left stray objects. Replaced with fsspec `autocommit=False` + `commit()`, which is atomic on both local disk and GCS with no branching. (3) fake-gcs hands out resumable-upload URLs at `0.0.0.0` unless told `-external-url http://gcs:4443`. (4) Emulator needs `FSSPEC_GCS_TOKEN=anon`; real GCP uses ADC.
- Other surprises: `docker compose run <svc> <args>` *replaces* the service's command, so job subcommands live in `entrypoint`. `/metrics` crashed on an empty bucket (a fresh deployment): History.load now handles missing datasets. Image is 207 MB compressed but 654 MB on disk (pyarrow + scipy + pandas + numpy ≈ 400 MB); matplotlib moved to an optional `report` group and third-party test suites are stripped.
- Open: SPEC's "image < 500 MB" doesn't say compressed vs on-disk; `make itest` needs uv on the host as well as Docker.
- Stage 3b: SPEC now says "< 500 MB compressed" and "Docker + uv" for a clean machine. Added `make demo` (fixture days → train → plan in the stack) and an optional Tiltfile whose buttons only call make targets. `tilt ci` brings the stack up healthy and runs the unit tests; `make itest` passes against a Tilt-managed stack too. Tilt respects compose profiles, so the jobs aren't started.

## Stage 2c — Model development (notebook-led)
- Checkpoint A: added jupytext-paired notebooks (`make notebooks`), a repo experiment log (`experiments/`, `flexcast backtest --experiment`), and a p10–p90 coverage metric in the backtest. `01_explore_prices`: the daily/seasonal shape is stable but day-to-day level is noisy (price correlation with itself: 0.84 at 30 min, 0.18 at 2 days); demand minus wind is the clearest driver; negatives peak at 12% of half-hours around 14:00 (solar) and spikes in the evening; imbalance vs exchange price correlate 0.82 with a ±£30 noisy gap. `02_diagnose_model`: baseline logged (£32.55/yr, MAE 30.6, coverage 66%); errors and upward band misses (up to 28% vs 10% target) concentrate in the evening peak; forecast daily spread is roughly half the actual; the worst 10% of days hold 29% of the missed £ (worst: a £800 evening spike forecast as an ordinary day).
- Process note: the baseline log entry recorded the last commit, but ran with uncommitted changes. Commit before every logged experiment from now on.
- Checkpoint B: NESO embedded solar + wind forecasts added (client, 2-year vintage backfill, 4 features, available at publish + 2 h). `03_solar_feature`: at the same demand-minus-wind, daytime prices are ~£28/MWh lower when solar is high, so NDF doesn't fully capture it; the model ranks embedded wind and solar 3rd and 4th by SHAP. Validation window: £24.6 → £28.5/yr, MAE 27.6 → 27.4 → adopted by the pre-set rule, though the bootstrap 90% interval (−£3 to +£11/yr) includes zero. Test year (logged as `solar`): £32.55 → £33.93, MAE 30.59 → 30.34, coverage 66% → 67%. Risk-aware alpha re-chosen on validation as 0.25 (£34.56 on test).
- Surprises: real-data validation earned its keep: NESO's "GMT" column was London time for a few vintages during a system migration (2026-04-20/21, rejected), and the archive has a 3-day gap (2025-05-09..11). Lesson: information that improves the average forecast barely moves £, because it doesn't fix the flattened spread or the narrow band. Watch `embedded_age_h` (may encode data gaps). Experiments now keep their own forecasts and model so notebooks stay pinned to the run they describe.
- Checkpoint C: tuning and calibration, both chosen on the validation window. `04_tuning`: £ resamples ±57% of its value over 182 days vs ±5% for pinball, so pinball selects and £ checks (across 13 configurations they ranked similarly, ρ = −0.78). Winner: strong regularisation (min 200 rows per leaf, L2 = 10, 150 rounds), validation pinball 8.37 → 8.12, £ 28.5 → 32.4. The mean-trained p50 didn't widen the daily spread (all variants ≈ £60 vs £120 actual); huber needs its threshold scaled to prices; dropping `embedded_age_h` made things worse. `05_calibration`: rolling conformal offsets, 90 days, whole day, band only won (coverage 72% → 82%, misses 9%/9%); per-block and p50 shifts distorted the daily shape and cost £. Test year: `tuned` £36.61 (MAE slightly worse, 30.34 → 30.46, pinball better); `calibrated` (production) pinball 9.28, coverage 77%, £ unchanged; α re-chosen = 0.
- Bugs caught on the way: band clamping vs re-sorting (re-sorting moved p50 under a band-only calibration); calibrated forecasts only on the test window broke α selection; the experiment log recorded the uncalibrated row. Each now has a test. Pinned notebook 04's pre-tuning settings so re-runs stay reproducible after the defaults changed.
- Where checkpoints A–C leave it: £32.55 → £36.61/yr (+12%), an honest band, but the forecast still flattens the day to half its real spread. That's the structural limit of predicting this price 15+ hours ahead, which is checkpoint D's question.
- Checkpoint D: the day-ahead auction (N2EX) becomes the primary market (SPEC §1 reframed). Facts first: bids close 09:50 UK time on D-1, results by 10:00 (Nord Pool), so 09:00 is the real deadline; NESO's `Date`/`Delivery Period` are **UTC** (undocumented; every day has 24 rows incl. clock changes, and the series lines up with Octopus Agile far better as UTC: residual sd 1.96 vs 2.74 p/kWh in summer). Built a timezone-safe client, a 2-year backfill (23/25 hours on clock-change days), six auction-price features (yesterday's are known at decision time), an hourly-block battery constraint (the auction trades whole hours), a market-aware backtest (labels known to D-1, not D-2), and switched train/plan to the auction market.
- Result (test year, logged as `day_ahead`): perfect foresight £69.61/yr vs £270.73 for imbalance, but the model captures **65.4%** (vs 13.5%) and so earns **£45.50** vs £36.61; naive copying of yesterday's auction prices *earns* £15.48 (vs −£148.66); MAE 12.4 vs 30.5; coverage 78%. Within each day the model ranks the auction's hours almost perfectly (median rank correlation 0.91 vs 0.50). The imbalance price's extra theoretical value is mostly spikes nobody can see a day ahead.
- Surprises: my notebook-06 draft claimed "similar daily spread" before seeing data; the auction's is half (£62 vs £123), so less value but capturable. PuLP 4 compares `var == var` as objects (needed `a - b == 0`). The exact NESO republication time doesn't affect results: at D-1 09:00 we only use D-1's prices, auctioned on D-2.
- Candidate inputs (after checkpoint D; `docs/candidate-sources.md`, notebook `07_gas_and_availability`): surveyed free sources a commercial forecaster would use, then built the two that need no sign-up and keep publish times: **gas price** (National Gas System Average Price; an undocumented CSV endpoint found by reading the portal's web app; gas day d appears ~12:40 UK on d+1, so at D-1 09:00 the latest is D-3) and **plant availability** by fuel incl. interconnectors (Elexon FOU2T14D; hourly vintages 2-14 days ahead), from which a margin (dispatchable + imports + wind − demand) is derived. Also measured NESO's day-ahead republication at ~12:30 UK (availability rule now 13:00).
- Result: **not adopted** by the pre-set rule. Validation: £29.89 → £29.65 (gas), £30.04 (availability), £29.78 (both); MAE never improved alongside £; bootstrap intervals ±£1.50/yr around zero. Test year (logged `cand_*`): gas cut MAE 12.43 → 11.82 and nudged coverage to 79%, but £ stayed ~£45.5-45.9. The model uses gas and margin heavily (SHAP 4th/5th), yet yesterday's auction prices already carry the gas level, and the battery trades the within-day shape.
- Surprises: gas was flat (~£25-30) across the whole validation window and nearly tripled during the test year, so the validation window simply couldn't test it; the test-year accuracy gain is real but choosing on it would be test-set selection. One leakage mutation (availability ignoring the time filter) first survived because vintages always predate the 09:00 decision; added an earlier-decision test. Open question: a longer history spanning the 2022 gas shock (day-ahead prices go back to 2021) is the proper test.
